## Git discipline

- **Commit often** at natural checkpoints, small and focused: per module/feature, per bug fix (with its regression test), per doc update. There is now a measured economic argument for this, not just a hygiene one — see below.
- **A commit issued as its own turn costs the whole session's context, and almost none of it is the commit.** Measured across 20 commit/ship/merge turns over 21 days: **10.35M weighted tokens, averaging 517K per commit turn** — and only **3.8%** of that was output. The other 96% split evenly between re-reading the accumulated conversation (48%) and re-writing the cache (48%). Committing is one of the cheapest operations git has and one of the most expensive turns you can take.
- **The cost is `round-trips × context size`, and both are yours to control.** The worst observed turn — `"commit everything so far"` in a ~700K-token session — took **44 API round trips and cost 3.0M weighted**, because every `git status`, `git diff`, file read, and re-check re-read the entire context at ~68K effective tokens *per call*. The cheapest commits were 1–4 round trips at 43–280K. Concretely: 6 calls at a 150K context ≈ 90K; 44 calls at a 700K context ≈ 3.0M. **That is a 33× spread on the same logical operation.**
- **Batch the git commands into one shell call.** `git add -A && git commit -m "..."` in a single invocation, not status → diff → add → status → commit as five turns. Verify after with one `git log -1 --stat` (which you need anyway, since `git add -A` obeys `.gitignore` silently). Do not run `git diff` to rediscover changes you just made — that re-reads into a context that already holds them.
- **Commit before the session gets large, not after.** The same commit is ~5× cheaper at 150K context than at 700K. This makes "commit at natural checkpoints" the cheap path as well as the safe one, and it pairs with the ~200K restart rule in [CLAUDE.md](CLAUDE.md) — commit, `/clear`, reopen.
- **Cache staleness is *not* the driver here — session size is.** Turns with a >60 min gap (dead cache) averaged 402K; turns with a warm cache averaged 538K. The intuition that "committing after a break is the expensive case" is wrong; the expensive case is committing late in a big session, whenever that happens.
- **Weigh the full `/ship` ritual against where the session already is.** Docs-update → tests → commit → push → PR → review → address feedback is dozens of round trips at maximum context, which is the most expensive possible moment to spend them. Running the ritual earlier, or splitting it (commit now, PR after a `/clear`), costs a fraction of the same work done at the end.
- **Messages explain *what* and *why***: "fix off-by-one in pagination when filter is empty," not "fix bug."
- **Never commit large binaries, downloaded data, or keys.**
- **Don't amend pushed commits**, and don't `--no-verify`. Fix the hook's underlying issue.
- **`git push` and opening a PR need their own explicit go-ahead — a general "keep going" is not consent for them.** (2026-08-29) After finishing a multi-step task, the assistant asked "want this shipped?"; the user replied "keep going" and the assistant read that as authorization for the full commit→push→PR→review chain, including publishing a branch and opening a real PR. Corrected: "don't automatically go to a PR without me telling you it's okay." A reply to an unrelated or generic offer doesn't satisfy an action this specific, even mid-workflow. Ask directly ("push and open a PR?"), or wait for the user's message to name the action itself (contains "ship", "push", "PR", or "merge") in that turn.
- **`git fetch` and integrate onto the latest remote before pushing to a shared branch.** Parallel agent / IDE / Codex sessions advance `main` mid-task; a stale base is rejected non-fast-forward. Check `git rev-list --left-right --count origin/main...HEAD`; if diverged with overlapping edits, re-apply onto the new structure rather than force-pushing (a force-push destroys the parallel work). At session start, `git branch -a` + `git log --all --oneline | head` to spot another tool mid-flight before assuming a clean starting point. Only clear a stale `.git/refs/.../*.lock` after confirming no `git` process is running.
- **Don't gate a commit on a piped filter.** `pytest … | grep passed && git commit` silently skips the commit when grep matches nothing (it exits non-zero). Run the tests, read the summary, then commit as a separate step.
- **Write save/restore, never an unconditional reset, for any re-entrant flag or context.** A `finally { suppressed = false }` inside a function that is itself called from a `withSuppressed(...)` block doesn't restore the flag — it *clears* it, silently re-arming the very side effect the outer block was suppressing for everything after that call. Real cost: every fresh page load pushed a spurious history entry, so the browser Back button stopped leaving the site. Always `const prev = flag; flag = true; try { … } finally { flag = prev; }`.
- **Your own review of your own diff is the weakest review you'll get — push early and let a cold reader (PR bot, teammate) read it before you merge on green.** Measured on one PR: an 8-angle self-review found 3 real bugs; the PR bot found 12 across 3 rounds, including 2 P1s, every one reproducible. The gap isn't effort, it's standpoint — you review the code against the model you already hold, so the misses cluster in what you'd stopped questioning (a field that's null on 45% of rows; a fragment scheme the router already owned; a `<form>` with one text input submitting on Enter). Your tests inherit the same blind spot: three of those bugs each had a *passing* test that exercised the one shape that happened to work. Budget a round or two of bot fixes into "done" rather than treating your own green suite as the gate. **Reproduce every finding before fixing and re-verify after** — it converts a plausible comment into a fact, and it catches your own half-fixes.
- **When a field's population varies across your data, a test that exercises one subset proves nothing about the rest.** A search covered `docket_full` but not `docket`; the test searched a FERC docket (which has `docket_full`) and passed, while **199 of 440 records** — nearly every state one, whose cards print the short `docket` and have no `docket_full` — were unfindable by the identifier displayed on screen. The suite was green and the headline feature was broken for 45% of the corpus. Before trusting a field-level test, count how many records actually populate that field (`sum(1 for r in data if r.get(f))`), and pick the fixture that *lacks* the field the code happens to read. Corollary: any user-facing promise ("search a utility, docket, or keyword") deserves a test per shape it claims to cover, not per code path.
- **An idempotence/skip guard keyed on a coarse marker skips a finer required update.** A "skip if already present" check keyed on `"WRAP 2.0" in career` skipped adding the *new* clause (shared DOE-EPA permitting tools + brownfield reuse) to 7 of 8 files, because the coarse token was already there from an earlier pass. Key the skip on the *specific new content* you are adding (`"EPA regional offices" not in career`), not a broad marker that predates it. Same family as the early-return "nothing changed" guard below.
- **An early-return "nothing changed" guard will hide the bug from your tests.** The above shipped under a green suite because the write path began with `if (encoded === current) return;` — true in every case the tests exercised, false only on the one uncovered edge (first load, before the value exists). When a function is guarded by an idempotence check, test the state where the guard *doesn't* hold; otherwise the tests assert the guard, not the logic.
- **Verify the files you think you committed are actually in the commit — `git log -1 --stat`.** `git add -A` obeys `.gitignore` **silently**: no warning, no error, exit 0. A repo's credential globs are deliberately broad (`*_token*`, `*_secret*`, `*_password*`, `oauth*.json`), and they match innocent filenames too: a `tests/test_tokens.py` (design tokens) was swallowed by `*_token*` and dropped from the commit that described it in detail — a fresh clone would have had the feature with none of its tests. **Never weaken the glob** to fix this; it exists to stop real credentials. Rename the file. Treat any filename that would trip a security glob as a file git will silently ignore.
- **A validation gate that only runs on `push` lets `main` silently freeze for weeks.** If a broken-link/schema check gates deploys but nobody runs it on PRs too, every merge since the first failure quietly stops shipping while the live site just stays frozen at the last good build with no alert. Run the identical gate on `pull_request`, not just `push`.
- **No agent co-authors and no machine fingerprints.** No `Co-Authored-By:` for any AI tool, no "🤖 Generated with…" footers, no generic-assistant PR prose. Commits are owned by the human who ships them; write messages in their plain voice. Enforce with `git config --local claude.coauthor false` (set globally once to cover all repos). A config change doesn't retroactively fix old commits: before cleaning up a repo's history, `git log --all` for existing violations first.
- **Verify local vs. remote before any multi-branch sync, cleanup, or merge.** `git fetch --prune`, then check `git status` / `git branch -vv` for divergence; don't assume local tracks remote. If both "ahead" and "behind" are non-zero, diff the actual file trees (`git diff <local> <remote> --stat`) before treating it as real conflicting work: it may be a stale local branch (e.g. from a local merge running in parallel with pushed PRs) that's safe to fast-sync. Treat `git reset --hard` used to reconcile as a destructive operation requiring the same confirmation as any other; surface what you found, don't do it silently.
- **The global `claude.coauthor false` fix doesn't reach cloud-hosted Claude Code sessions.** A local `~/.gitconfig` setting only applies to commits made on this machine. Commits from a `claude.ai/code` cloud session (branch names like `claude/adjective-noun-hash`, sometimes with an explicit `Claude-Session:` trailer) run in a separate sandbox that never sees this machine's global config, so `Co-Authored-By:` and model-name trailers still leak through there. A week's sweep across several repos found ~15 such commits despite the global config being set locally. There's no config-level fix for the cloud side yet; catch it at PR-merge time (edit the merge-commit message) or with a post-merge cleanup pass, since the trailer is otherwise invisible until someone reads `git log`.
- **The same sandbox gap corrupts the actual commit *author*, not just the message trailer — and it recurs daily if the automation doesn't self-configure.** A recurring scheduled/cloud-run task (a data-refresh skill invoked from a `claude.ai/code` Routine) has no ambient git identity, so it commits as its own default bot account (`Claude <noreply@anthropic.com>`) every single run — found across 3 repos, in one case going back to the project's inception. Rewriting past history doesn't fix this; the automation's own commit step must set identity itself. Add `git config user.name "<username>"` / `git config user.email "<id>+<username>@users.noreply.github.com"` — **local, not `--global`** — immediately before `git add`/`git commit` in the skill's own instructions, so it's correct in any environment (local machine or a fresh sandbox) without depending on ambient config.
- **Set commit identity deliberately.** Author with the account's noreply address, `git config --global user.email "<id>+<username>@users.noreply.github.com"`, and set `user.name "<username>"` too, or git falls back to the OS full name and leaks it. The human runs this; agents don't touch git config.
- **A session-start git snapshot is a point-in-time claim, not current state. `git fetch` before you measure, plan, or build against it.** A worktree whose status header read clean-and-current was ~100 commits and 3 months behind `main` (the corpus had grown 107 → 168 records) because the repo has a scheduled sweep that commits daily. Six specs were written and every number in them measured against that stale tree; the plan they implemented had **already been written and merged** as an earlier PR. Nothing surfaced it until `gh pr merge` hit a conflict, near the end. `git fetch origin && git log --oneline HEAD..origin/main | head` costs two seconds. Corollary, and the cheaper of the two checks: **before implementing a plan or spec, look for it on the remote** — `git ls-tree -r origin/main --name-only | grep -i <plan-dir>` — because the work you're about to do may already be done. The stale-snapshot risk scales with the repo's commit cadence, so treat any repo with automation that commits on a schedule as stale by default.
- **`gh pr merge --delete-branch` fails inside a worktree when the target branch is checked out elsewhere — but the merge already happened.** The error is `failed to run git: fatal: 'main' is already used by worktree at …`, which reads like the merge was rejected. It wasn't: GitHub merged it, and only the *local* branch-cleanup step failed. Confirm with `gh pr view <N> --json state,mergedAt` before reacting, then finish the cleanup by hand with `git push origin --delete <branch>`. Retrying the merge on the assumption that it failed is acting on a false premise.
- **Poll CI with `until ! gh pr checks <N> 2>&1 | grep -q pending; do sleep 15; done`.** Extracting a single status field (`awk '{print $2}'`) works until the PR has more than one check, then the comparison sees several lines at once and the loop exits immediately or errors. Grep for the state you're waiting to *leave*, and let it match anywhere in the output.
- **Don't delete an unmerged branch just because its PR was closed as superseded** — closing and deleting are different decisions, and only one is reversible. Verify with `git merge-base --is-ancestor <branch> origin/main` before any delete; if it isn't an ancestor, the branch holds the only copy of that work. Keep the local branch and say so, rather than making the call silently.
- **Fold a parallel background-session branch into the active PR with `git cherry-pick`, not a merge or a second PR.** A spawned background task (a separate worktree/branch) that fixes something unrelated to the main branch's work still usually shares the same base commit — confirm with `git merge-base`, then `git cherry-pick <sha1> <sha2>...` onto the active branch. Cleaner than merging (no merge commit, no risk of dragging in unrelated history) and avoids juggling two open PRs for what's really one review unit. Once tests pass and the branch is pushed, `git worktree remove` + `git branch -D` the now-redundant branch — don't leave it dangling as a second source of truth.

- **`git diff main...branch` cannot tell you whether a branch is merged — and it reads like it can.** Three-dot diff means "what this branch changed since it diverged", so a branch whose work was **squash-merged** long ago still reports a large, confident-looking diffstat. Two branches were reported as holding 9 unmerged commits and ~420 changed lines on exactly that evidence; all 9 were already in main under different SHAs. `git branch --merged` misses squash-merges too, for the same reason (no shared commit). Verify by **substance**, not by diffstat: for each commit, grep main for the feature it claims to add (`grep -q "function parseHash" theme.js`), then `comm -23 <(git ls-tree -r --name-only $branch|sort) <(git ls-tree -r --name-only main|sort)` for files that exist only on the branch. That pair answers the real question in seconds and is the only evidence worth deleting a branch on.

**2026-08-05**

- **When a PR is already open for a workstream, push the follow-on work to that PR's branch — do not open a second PR.** Implementing a spec that was itself an open PR, I merged its branch into a new branch and opened a second PR, leaving two PRs describing one piece of work and making the first look abandoned. The reviewer loses the thread from spec to implementation, CI doubles, and the review bot restarts from zero instead of building on what it already commented on. Check `gh pr list --state open` before opening anything; if an open PR already covers this workstream *including its planning stage*, commit to its branch. Open a second PR only for genuinely separate work, and ask if unsure.

**2026-08-09**

- **Backticks in a commit message passed with `-m` are command-substituted by the shell, and the message is silently shortened.** Writing ``an author `display:` rule`` produced `command not found: display:` on stderr and committed the sentence with the phrase *deleted* — the commit succeeded, so nothing looked wrong until the message was read back. Any message containing backticks, `$`, or `!` goes in a file and is passed with `-F`; verify with `git log -1 --pretty=%B` before moving on.

**2026-08-10**

- **`.gitignore`'s `dir/` does not match a symlink named `dir`.** A `.venv` symlink pointing at another checkout's interpreter was committed straight past a `.venv/` ignore rule, because git sees a symlink as a file and the trailing slash means "directory only". It also carried a machine-local absolute path into history, which the repo's own hygiene test could not catch — that test reads file *contents*, and a symlink has none. Either drop the trailing slash, or put the symlink in `.git/info/exclude` (which is per-clone and never committed, the right home for a local convenience).
- **Squash-merge detection needs two independent signals, because each one goes blind at a different moment.** A DryDock merge sweep classified branches by comparing local refs against `main`; once `main` advanced *past* the squash commit, the ref-based check stopped recognising the merge and the branch reverted to looking unmerged — the same failure that had already broken version 2 of the script. Neither the ref comparison nor the content/patch-id check is correct alone: the first goes stale as `main` moves, the second goes blind when later commits touch the same lines. **Accept the branch as merged if *either* signal says so**, and emit a distinct `unreadable` state for refs neither can classify rather than skipping them — a ref silently omitted from a merge report reads exactly like a ref that was checked and found clean.
